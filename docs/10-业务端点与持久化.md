# 业务端点与持久化

本章整理启动后的 CN3.5 业务契约。路径和客户端消费、本项目实现、历史验证是三个层次。未确定的官方语义继续保留为暂定；日期较早的文档“排除项”只描述当时任务范围，不代表当前源码必定没有该端点。

## 端点族与状态源

| 端点族 | 输入／输出重点 | 状态源 |
|---|---|---|
| `/user_units`、`/user_monsters` | 库存、面板和行为参数 | 账号库存 × 静态模板 |
| `/user_decks`、`/user_decks/on`、`/user_decks/off` | 有序 parties、实际队伍键和槽位 | 独立账号编队 |
| `/stages`、`/areas`、`/quests` | 目录与账号解锁 | 静态目录 × 玩家进度 |
| `/quests/execute/<id>.json`、use_ap、result、lose、continue、log_battle | 会话、扣点、结果与归档 | 战斗状态 × AP × 奖励快照 |
| `/gachas`、`/gachas/execute`、`/users/reload_data` | 池表、结果、缓存重载 | 发布配置 × 账号经济 |
| `/users/messages` | 按类别的消息队列 | 内容池与推送节奏 |
| `/act_pages` | 活动横幅和页面入口 | partials 与静态页面配置 |
| `/user_presents/receive/` | 单领／全领及剩余礼物 | 领取状态 × 账号资产 |
| `/chapters/`、`/stories/list`、`/stories/read/<id>.json` | 章节、排序、阅读与续读 | 使用者准备的故事材料与资源 |
| `/user_items/`、`/medal_items/`、`/medal_items/exchange` | 背包、分组商品和兑换 | 物品库存 × 发布快照 |
| `/user_units/training` | 正常等级训练 | 当前等级 × 金币余额 |

逻辑读面也可能通过外层 POST 请求，注册方式以实际协议为准。空列表可以表达未实现的读面，不能对经济写操作返回伪成功。

## 编队对象的顺序

`data.user_decks.parties` 是有序对象，不是数组。客户端按 JSON 解析顺序生成轮盘序号，服务端应按 display_order、party_id 输出专门的有序序列化，不能让 Go map 的键排序代替游戏顺序。

on/off 接收真实 party_id、0 基 party_index 与 unit_id。on 校验持有、槽位存在、同队不重复；off 校验槽位当前值。校验和写入同一事务，空槽位保留空字符串。初始两队五槽、首队按实际库存填充属于重建策略。

开战的 party ordinal 需要先映射为同一显示顺序的队伍，再读槽位与库存。不相信客户端上报的全库存列表就是实际出战单位。

## 战斗与经验

execute 返回战斗文档和服务端指定的扣点／结果／失败地址；后续不能随意切换为另一个账号或关卡。battle_id 必须绑定当前账号，状态迁移与 AP、奖励、通关和进度共同提交。

用户经验在 result 逐级结算，维护 profile.level/exp/max_exp 与两档 exp_table 窗口；2100 封顶后的冻结是重建规则。资源副本奖励在开战时固定配置版本，结算不再按最新发布版重新摇奖励，且不推进剧情 next_quest。

battle_record 是归档材料，实际记录不进入公开文档。不能因为协议返回 HTTP 200 就推断奖励、状态或持久化正确。

## 抽卡的页面消费

客户端单抽携带 id、count=1，连抽携带 count；可选 use_scout_book 是否支持由业务实现明确拒绝或接受。池 id 应为 JSON number，单抽的整数访问与连抽的字符串访问才都能读到；字符串 ID 可能导致单抽读成零。

requireData 的 gachas 可能被 preset 缓存提前满足，也可能真实请求 `/gachas`。验证接口覆盖时要观察实际请求，不能只看响应模板。

available_list_option 作为附加页面配置提供名单列表；data_key 指向同源缓存键。详情按钮的动作 method 与 PageMessage 的导航 method 是不同概念：ShowRule/ConfirmModal 等动作分派，不能直接拿 Stack 替代。

同一 list_type_id 映射槽位不能重复注册。结果列表必须非空，客户端按 rare_type_id 排序展示，不一定保持随机抽取顺序。余额应通过 data.user 和 data.user_coin 回推，展示价格与实际扣费来自同一规则源。

## 抽卡幂等的实际能力

客户端既有请求没有可靠的业务 transaction_id。相同账号、池、次数和秒级时间可能同时表示网络重发或合法再次抽取。不能仅靠参数摘要就宣称严格识别用户意图。

本项目采用有界重放：账号锁内结合最近已提交操作、重试窗口和失败后的 `reload_data?on=gachas_execute` 信号判断是否返回原快照。摘要用于规范化请求，服务端 nonce 形成操作审计键。没有被判为同一操作的请求按新抽处理。

内存时序在重启后会丢失，某些无键跨重启请求可能按新操作结算；事务幂等保证已经识别的操作不重复提交，并不覆盖所有无法区分的意图。用户合法再抽也不能永久被同参摘要吞掉。

抽卡事务内完成条件扣费、发卡、保底、操作快照、逐抽与流水。重复副本不重置旧卡等级、保护或魔宠装备；满觉补偿规则属于重建经济。原材料的概率、保底和价格是提案／实现值，不作为官方概率公示。本章不把早期四槽描述当成所有部署的当前生效卡池。

## 字符串与协议兼容

已有分析记录旧 JSONObject 对字符串中的不平衡括号有兼容问题。服务端通过 `cn35wire` 的统一序列化处理相应文本，平衡文本保持原样。不要在每个 handler 里各做不同的字符串修补，也不要把实际报错日志和原作文本复制到公开说明。

## 同伴和魔宠写面

| 路径 | 主要参数 | 关键约束 |
|---|---|---|
| `/user_units/set_leader` | id，兼容 card_id | 单位必须属当前账号；不清空 helper |
| `/user_units/set_helper` | id | 与 leader 独立；同一单位可兼任 |
| `/user_units/protect` | unit_id、protected | 写持有行的保护状态 |
| `/user_monsters/on` | uuid、unit_id | 同账号，一对一，旧宿主／旧装备一起更新 |
| `/user_monsters/off` | uuid、可选 unit_id | 提供宿主时必须与实际匹配 |
| `/user_monsters/protect` | uuids[]、protected | 批量任一归属失败整体回滚 |
| `/user_units/training` | id、before、after | before 陈旧拒绝，目标在当前觉醒上限内，扣费与等级同事务 |

helper 为空时省略对应 wire 键，leader 保持既有非空约束。魔宠 on/off 同时维护 monster.unit_id 与 unit.monster_uuid，不能只改一边。已有客户端解保护会发 `fasle` 拼写，应按已确定的兼容规则处理，不把它修成不认识的新请求。

潜能、进化、出售和分解等缺规则的写面明确 modal 拒绝。早期资料称觉醒未开放，后续已有暂定 awake 实现；应分清本项目行为与尚未确认的官方上行路径。

## 礼物领取

单领携带 uuid，全领不带 uuid，without_unit=true 可排除同伴礼物。响应包含 status、rewards、modal_title/modal_body 和更新后的 data；user_presents 是剩余未领列表。

rewards 行包括 type/id/count 和渲染需要的 message/rare_type_id。没有可靠来源时，不填 icon_asset_name 覆盖客户端按类型和 ID 推导的图标。

领取标记与奖励发放同事务。未知 UUID、他人礼物、过期、已领取和不支持类型明确失败；全领可跳过过期／不支持项，仍保持未领取。旧版本支持 unit、monster、coin、gacha_point，后续扩展 medal/item；不能把早期类型范围当作永久限制。

同伴副本与抽卡复用结算原语，魔宠每份建独立实例。标记已领不能脱离发奖独立提交。

## 任务附加页面选项

`/quests/current_quest_additional_option?quest_id=` 返回 current_quest_additional_option 顶层键，并可在 data 中回推同名缓存。客户端检查响应根，不能只包在 data 下。

该选项的 parts、requireData、data_key 和关卡 id 应与列表入口同源，避免同关从两个入口进入却选到不同 execute 行为。

## 消息与活动

messages 以类别为键，空类别保留空数组。单条字段有 id、text、user_name、user_id、created_at；这里只说明 schema，示例中不含真实发言、昵称或账号。

本项目按账号控制推送间隔和数量，避免客户端队列增长导致显示更新加速和卡顿。内容池未装配时回空，不伪造玩家聊天。历史固定种子消息也应明确是合成内容。

act_pages 由 partials 与横幅资源驱动。入口配置能打开不等于对应活动玩法已实现，尺寸和素材加载需要实际客户端核对。

## 阅读与续读

章节行的 chapter_select_option 注入 Stories 的 requireData 与 ListParts.data_key，通常使用 `stories_<chapter_id>` 缓存键。故事行带 chapter_id、order_num 和阅读附加消息；续读依赖相同章节缓存与顺序。

read 响应直接提供 story、asset_names、actress_xys，不能包成普通 data 信封；不存在的故事应失败，不返伪造空剧本。chapter_id 缺失会使续读链路失效，标题中的 PageMessage 分隔字符也要处理。

加载时校验故事 ID、场景与排序唯一性，及演员、背景、坐标和 asset_names 的资源闭包。缺失或全部剔除时章节可以回空。仓库不包含剧情正文；使用者自行准备合适的内容和资源。旧“全部开放”目录策略不读服务端已读进度，不能宣称已经实现服务端阅读存档。

## 物品、资源副本与徽章兑换

物品读面输出 user_items 与分组 user_items_hash。分组键 1–7 的存在影响客户端按钮，分类归属和某些行字段仍包含本项目暂定映射。素材 powerup_items 与潜能 upgrade_items 是不同来源。

资源副本通过 stage/area/quest 目录合并层开放，复用战斗链。掉落概率与波次缩放为重建配置，开战时保存奖励快照，结算时按 item/content_id 入库或计入余额。

medal_items 响应包含商品分组，exchange 接收商品 id、count 与可选 request_key。扣徽章、入账、限购计数和奖励台账共同提交。显式键同参可重放、同键异参拒绝；没有稳定键的客户端调用只具备对应在途去重与业务约束。

awake 的觉醒书消耗与上限是本项目暂定规则，真实上行路径和物品编号不能只靠实现代码证明。本文只覆盖运行时业务端点，不涉及配置发布与发放的管理接口。

## 验证范围

历史记录中有单位列表、编队、训练、抽卡、故事阅读和部分剧情胜利的设备验证；失败／续战、不同资源与多章配置的完成范围不一致。这些验证未在客户端重跑，零散结论不能扩展成全游戏已恢复。

新增端点应核对实际注册、鉴权、JSON 类型、持久化写入、重复提交与账号隔离。缺数据应保持明确空态或拒绝，不能因为路由存在就计作玩法完成。
