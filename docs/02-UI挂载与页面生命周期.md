# UI 挂载与页面生命周期

CN3.5 页面由服务端 `app_conf` 配置驱动，客户端负责加载 prefab、创建部件和导航。配置正确与否，首先取决于对象实际挂在哪棵 Transform 树上。本文整理静态分析的结论，不复制客户端源码，也不据此宣称所有页面已经实机验收。

## 对象归属决定清理范围

`pagePartsList` 和部件上的 `page` 引用表达逻辑关联，不能证明部件属于页面的 Transform 后代。销毁页面根时，Unity 会连同根下的对象一起清理；落在场景根或 `Common` 下的对象，需要其他清理流程负责。

| 归属 | 典型对象 | 离开页面后的行为 | 配置与验收要求 |
|---|---|---|---|
| 全局 `Common` | HUD、共享头尾、背景、弹窗 | 单页销毁后仍存在 | 明确重载、隐藏或重置规则 |
| 页面局部 | `PageBase` 及其后代 | 随页面销毁、退栈或缓存 | 每个动态部件核对页面内 parent |
| 部件局部 | `BasicParts/tempTr`、列表 grid | 随所属部件处理 | 子对象继续落在部件树中 |
| 临时对象 | 故事 viewer、特效、选择窗 | 取决于实际宿主 | 检查关闭钩子与回调绑定 |
| 缓存页面 | `cachePageBaseTr` 下的页面树 | 停用后复用 | 离开时不可见，复用时恢复当前状态 |

每个动态对象都应能够回答：父节点是谁、谁负责关闭、返回时是否复用。仅凭画面位置，无法判断所有权。

## 全局宿主与共享部件

`Common` 保存当前页、页面字典、缓存及全局 UI。场景中的 `Common/HUD0..HUD9` 与页面 prefab 内同名 `HUD0..HUD9` 是不同节点。普通部件的 `parent:"HUD9"` 从当前页面根解析，不能拿它指代全局 HUD。

| 全局位置 | 典型职责 | 切页时需要注意 |
|---|---|---|
| HUD0 | Modal、Loading、教程、临时详情窗 | 页面关闭不等于弹窗关闭 |
| HUD1 | 触摸保护层 | 恢复可交互状态 |
| HUD2 | 转场 | 按转场流程关闭 |
| HUD3 | 未指定页面宿主的 StoryViewer | 必须终止或销毁 |
| HUD4 | Overlay、SelectModal | 关闭遮罩、重新绑定筛选回调 |
| HUD5 | Header、Message | 重新加载当前页选项 |
| HUD8 | Footer | 重载导航和描述 |
| HUD9、L 层 | 低层内容或触摸例外区域 | 按具体脚本和场景关系核对 |
| L20 | Background、Weather | 全局对象，内容由当前页驱动 |

五个固定共享键是 `Header`、`Footer`、`Message`、`Background`、`StoryTrigger`。初始化页面时引用已有对象，不是每页各创建一份。`Weather` 也走特殊分派，但不属于这五个固定共享键；天气自己的创建和清理逻辑要单独检查。

共享对象不走普通部件的通用 Transform 更新。普通 `parent/x/y/z/scaleX/scaleY` 规则不能直接套到它们上。切回父页时要重新加载共享选项；每页应显式指定必要的显示状态、标题和背景，避免继承上一页的文案或按钮。

Header 返回按钮由 `Stack/SlideIn` 导航方式决定，不能只靠 `display_back_button` 配置控制。`StoryTrigger` 的 parent 用来选择故事 viewer 的页面内宿主，是脚本专用行为。

## 页面内的挂载链

正常层级可以表示为：

```text
Common.pageBaseTr
  └─ PageBase
      └─ 页面 prefab 内的 HUD/L 容器
          └─ PageParts
              └─ widget、列表行或局部辅助对象
```

页面根创建后挂到 `pageBaseTr`。普通部件从资源实例化时，并不保证自动成为页面后代；其选项加载时，才按 `parent` 查找当前页面根下的节点。缺少 parent，或路径不存在，都可能让部件游离于页面树外。

以下为独立编写的配置示意，资源名仅为占位：

```json
{
  "ExamplePart": {
    "prefab": "Common/PageParts/ExamplePart",
    "parent": "HUD9",
    "x": 0,
    "y": 0,
    "z": 10,
    "scaleX": 1,
    "scaleY": 1
  }
}
```

先核对真实容器，再调坐标。父层的 z 和 scale 会影响局部坐标含义；已有 Basic 页面中 HUD9 的 z 补偿常采用 `z:10`，这只是特定层级的经验值，不是所有 prefab 通用的层号。

## widget、列表和 partial 的区别

`BasicParts` 的动态 label、sprite、texture、imageButton 通常落在其 `tempTr` 下。通用 widget 变换处理位置、旋转和缩放，不消费任意 `parent` 字段。要改变这组 widget 的归属，应先让部件根正确落在页面中。重载选项会重建 tempTr 内容，不等于关闭整个部件。

列表行创建时会挂到 grid，因此跟随列表生命周期。列表的 `components` 则不能仅因写在同一个 JSON 对象中就认为是列表后代；它们需要各自检查 parent。组件创建的弹窗和按钮还要继续核对宿主。

`partial` 是配置模板展开，不能充当 Unity 父节点。展开后的每个实际部件仍应有自己的 prefab、parent 和显示规则。全局 partial 修改可能影响多个页面；轮播 banners 还可能被提升成全局配置使用。

## 四类导航与返回行为

| 流程 | 旧页面怎样处理 | 对部件的要求 |
|---|---|---|
| `Show` | 替换、销毁或移入缓存 | 页面后代随根处理；全局和游离对象另行清理 |
| `Stack` | 父页保留，移到后景并淡出 | 父页内容必须在自己的树中，防止穿透显示 |
| `SlideIn` | 新页滑入，仍有父子导航关系 | 返回时关闭或缓存子页 |
| 缓存与复用 | 页面根停用后重新初始化或重载 | 清理旧选中态、数据和回调，不能假设全量重新实例化 |

返回父页会重新加载共享部件，也可能继续使用原有局部部件。修改配置后只按返回键，不能证明配置已作用；需要重新创建页面或冷启动核对。

准备阶段取消与正常关闭是不同路径。取消准备可能直接销毁创建中的非共享部件；正常关闭主要销毁页面根。前者没有残留，不能证明后者的父子归属正确。

## 全局弹窗与配置污染

Modal、Overlay、SelectModal 通常由 Common 持有。切页时要验证它们是否关闭、回调是否仍指向旧页、触摸保护是否释放。多行筛选共用选择窗时，需要在点击时绑定当前行选项；排序组件可能还有独立选择窗。

基础页面配置与 `additionalOption/displayMode` 的合并，不应假定每次都深拷贝。现有静态分析显示基础 Document 可能保持底层引用，模式切换存在同进程污染风险。服务端应输出完整且独立的页面选项，并用“普通→模式 A→普通→模式 B”的序列检查，不通过修改客户端业务 DLL 规避。

app_conf 版本变化、缓存过期和页面重新创建是不同事件。版本号可以促使重新获取配置，却不保证已有页面实例立即重建。

## 配置修改的检查顺序

1. 画出 owner 和 Transform 父子关系，确认页面 prefab 的可用容器。
2. 分清共享部件、普通部件、widget、列表行、components 和 partial 展开项。
3. 检查父节点的 z、scale、panel、pivot，再调整坐标和点击区域。
4. 覆盖整页替换、入栈返回、缓存复用、模式切换、加载取消和冷启动。
5. 检查旧页面是否不可见、全局弹窗是否关闭、触摸是否恢复，以及是否发生重复按钮或回调。

配置字段存在并不证明客户端消费它。对没有消费依据的字段，不用“试着加一个键”替代链路核对。所有恢复调整通过服务端页面配置和下发实现。
