# 成长面板与战斗数值

本文说明 CN3.5 客户端消费的数值语义，以及本项目的重建口径。公式用独立数学表达整理，不包含反编译源码。静态分析能够说明客户端怎样计算，不能证明原服务器使用了相同的存储或结算实现。

## 服务端与客户端分别负责什么

| 环节 | 负责方 | 输入与输出 |
|---|---|---|
| 当前单位面板 | 服务端 | 按模板、等级和觉醒生成 `hp/at` |
| 成长区间 | 服务端下发 | 最小值、未觉醒满级值、成长类型和基础上限 |
| 升级预览 | 客户端 | 用区间字段插值，不把算好的面板上报 |
| Guts、属性、技能和实时伤害 | 客户端 | 在当前面板上叠加战斗上下文 |
| 结算和持久化 | 服务端 | 校验战斗归属与状态，发奖、升级和推进进度 |

战斗上报主要是标识和结果摘要：胜负地址、时间、剩余怪物数、撤退状态。可选 `battle_record` 提供更细的记录，但它的客户端响应不被用于继续推进结算；不能据此推断原服一定不使用该记录做反作弊。

## 单位字段分组

| 用途 | 关键字段 | 要求 |
|---|---|---|
| 当前战斗面板 | `hp`、`at`、`attack_ms`、`cost`、`speed`、`reach` | hp/at 是当前等级面板，attack_ms 单位是毫秒 |
| 成长预览 | `hp_min/hp_max`、`at_min/at_max`、`growth_type_id`、`base_max_level` | 区间端点与成长类型同时下发 |
| 等级和觉醒 | `level/max_level`、`duplicated_count/max_duplicated_count`、`hp_15_max/at_15_max` | 正常等级、当前觉醒上限和满觉上限分开 |
| 潜能 | `upgrade_level/max_upgrade_level` | 与正常 level 是不同状态 |
| 属性 | 五系 `*_rate` 与 `*_guard_rate`、`attr_id` | 攻击补正与受击抗性不同 |
| 动作与效果 | `hit_frame`、`multi_hit_count`、`multi_hit_interval`、动作帧和特效参数 | 用行为目录补足，不能由面板推导所有字段 |
| 展示 | `rare_type_*`、`country_id`、`weapon_id`、`hits`、`taghness` | 展示字段不自动等于战斗字段 |

五属性 ID 为炎、水、风、光、暗，对应 1–5。社区字段 `aqua` 在协议中映射为 `water_rate`。`hits` 的列表展示不能代替 `multi_hit_count`；`taghness` 是协议既有拼写，不能自行改成另一种英文拼写。

## 未觉醒区间的成长曲线

令 `m` 为 Lv1 值、`M` 为未觉醒满级值、`L0` 为 `base_max_level`，`L` 为当前等级。对 `1≤L≤L0`：

```text
x = (L - 1) / (L0 - 1)
p = 0.5（早熟），1.0（平均），1.6（晚成）
面板(L) = trunc(m + (M - m) × x^p)
```

`trunc` 为向零截断，正数时等同向下取整。`L0` 应至少为 2，避免除零。成长类型 1/2/3 分别对应早熟、平均、晚成；不能把所有类型都改成线性插值。

客户端直接使用服务端的 M，不按稀有度或成长类型再次乘满级倍率。本项目从社区规则推导 `M=floor(m×f)`、`f=1.8+0.1×type`，这是端点重建策略，不是所有单位原服满级表已获证的结论。

## 超过基础上限的线性段

当 `L>L0`，先取基础满级面板，再加超出部分：

```text
每级增量 = integer_divide(M - m, L0 - 1)
面板(L) = M + 每级增量 × (L - L0)
```

这里先做整数除法、后乘等级差，与全部浮点计算后一次取整并不等价。HP 与 AT 分别计算。服务端兼容时还应检查单精度中间值造成的边界差异。

本项目的上限关系为：

```text
基础上限 = 20 + 10 × 星级
当前上限 = 基础上限 + 已觉醒次数 × 5
满觉上限 = 基础上限 + 允许觉醒次数 × 5
```

五星基础 70 与已有样本相符，满觉 145 与客户端单位经验表的 145 项互相支持；其他星级与觉醒次数上限仍包含社区推导。下发 `max_level` 使用当前上限，训练只接受该范围内的等级。潜能升级的技术力预览另有变体与换算参数，不能复用正常等级写面。

## 魔宠 Size

玩家魔宠以 Size=1.000 的基础值为输入：

```text
hp = floor(base_hp × size)
seed_at = floor(base_seed_at × size^2.36)
```

显示体型 `scale` 和计算推进 `real_scale` 有不同用途。Size 应用十进制精确形式持久化；协议输出的 JSON 类型仍须满足客户端访问器，不能因为数据库存 TEXT 就推定客户端能正确读取数字字符串。

已有静态分析记录普通档阈值为 1.35/1.55/1.70，新档为 1.549/1.699/1.799/1.899/2.099/2.299；普通步长 0.02，新档 0.01。强化成本来自 `rare_monster_category_config`。这些档位不是关卡 `powerup_conf` 提供的。

社区魔宠目录没有完整初始 Size 来源；缺失时只能显式声明 1.000 降级，不能伪造稀有标志或体型上限。玩家魔宠面板与关卡敌方模板是两套上下文：关卡的 `scale/powerup_rate` 不能直接拿来当玩家魔宠的持久化体型。

## Guts、属性和外皮

Guts 从 1 开始，主要关系为：

```text
HP/攻击倍率 = 1 + (guts - 1) × 0.1
攻击间隔倍率 = 1 - min(guts - 1, 10) × 0.04
```

间隔到 Guts11 时达到 0.60；上限由 `consts.max_guts_up_count` 参与控制，不能假定所有调用点都使用同一个硬编码上限。每次升级回复与最大 HP 的增量有关，既有路径按增量的 5 倍处理。虚弱和攻击强化还会进一步影响实际攻击。

属性补正按单位自身五系基础倍率、属性升级加成和关卡弱化／强化加算，最后与 0 取最大值。治疗分支不包含攻击分支的全部关卡修正。技能层数上限没有被这条公式统一规定。

武器 ID 1–7 为 Slash、Rush、Hit、Arrow、Magic、Gun、Heal。外皮 ID 1–3 为 Soft、Normal、Hard，4–7 为 SoftL2–L5，8–11 为 HardL2–L5。不能沿用另一版本的五档 ID 顺序。

客户端可按服务端 `hardness[].bonus_rates` 查表；未启用完整表时存在粗略回退：Slash/Arrow 对软 1.2、硬 0.8，Hit/Gun 相反，其他默认 1.0。一旦启用服务端表，缺少的武器键可能退回 1.0，从而改变旧回退。原始完整倍率未取得前，本项目默认不发该表；显式测试配置必须标为重建值。

## 伤害管线和取整

普通攻击每段的基础量是：

```text
实际攻击 × 0.2 × 对目标属性补正 / 段数
```

之后依次施加约 ±5% 随机变化、适用的武器外皮与关卡武器倍率、暴击、部位倍率、残血强化、减伤和受击方属性抗性，最后向零截断。单位攻击怪物才走所述外皮分支；暴击命中时乘 1.5。残血强化与缺血比例及 `berserk_rate²×8` 有关。治疗具有相似的基础量和随机项，但不直接套用外皮和暴击。

不能用“单次伤害应等于面板攻击”验收。应先核对库存、详情、preset 和 execute 的 HP/AT 同源一致，再在固定战斗条件下核对伤害区间和变化方向。

技能不是统一的攻击函数。已有消费逻辑中，某些技能以 `A=2×实际攻击` 计算 `A×A^p1×p2×(1+p3/A)`，复唱类还除以 p4；攻击强化则有立方根形式的增量。参数必须按技能类型装配，不能将某个 `sklmax` 一律解释成百分比。

## SP、召唤和种子技

| 环节 | 客户端行为 |
|---|---|
| 开场 SP | initial_power，加上编队 bonus_sp、bonus_sp_rate、同国修正与额外 bonus_sp_add |
| 同国修正 | 以数值 country_id 计数；2/3/4/5 人对应 +5%/+10%/+20%/+30%，还受功能开关控制 |
| 战斗增长 | 击杀奖励的 power 按 SP 升级表倍率增加；不是自动随时间恢复 |
| SP 升级 | `powerup_conf[等级].next` 决定成本，`rate` 决定倍率 |
| 召唤 | 点击单位按钮消耗 unit.cost；装备种子技依赖宿主已上场 |
| Guts 升级 | 按 cost、当前士气及 0.2 系数计算消耗 |
| 种子技 | cost_rate 修正消耗，call_interval_ms 和 call_interval_rate 控制冷却 |

`country_id` 必须是客户端整数访问器可读取的数值类型。魔宠冷却从社区秒值转毫秒时，已有样本提示单精度中转再截断可能得到 21899，而双精度直接计算为 21900；复现时不能忽略这一差异。

本项目曾采用 `cost/bonus_sp=100×星级`、部分新手关 initial_power=500，以及补充逐怪 SP 掉落。这些是重建策略，不代表官方经济数值。自动出场的剧情单位和 NPC 援军，不应与玩家编队手动召唤混为一谈。

## 三套成长状态与用户经验

正常单位等级使用 `/user_units/training?id=&before=&after=`；潜能使用 `/user_units/upgrade?unit_id=&after_level=`；觉醒次数有独立消耗与上限。请求通常携带目标等级而非已计算面板，服务端应自行校验成本、当前状态和模板。

用户 rank 与单位等级分开。用户经验由战斗奖励推进，持久化在 profile 的 `level/exp/max_exp`。已接入的社区曲线覆盖 1–2100 级：1–5 级每档 100，6 级 400，100 级 27690，1000 级 1180590，之后分段需求，2100 封顶。迁移 0022 用当前等级回填旧 max_exp，运行结算逐级扣需求，并维护下一档窗口 `exp_table`。封顶后冻结经验是本项目策略，并未逐级实机确认。

## 实现、历史验证与未决项

`server/internal/statmodel` 已把成长和 Size 计算收敛为纯函数。记录中的单位样例 152：Lv1 HP/AT 为 3680/3600，Lv70 为 7728/7560，Lv145 为 12078/11835。既有训练验收曾核对 Lv4 的 3706/3626 与数据库扣费和等级一致；这只说明该样例及所测分支，不承诺全表与原服逐位一致。

早期分析有“面板仍为 Lv1、成长字段缺失”的基线，后续已修复，本文不把该历史基线当作现状。Size 列已建立，但初始真值、完整外皮表、潜能配置、技能参数与部分养成上行仍需单独核实。觉醒路径后续出现本项目暂定实现，不据早期“未开放”结论推断永久缺失，也不把暂定路径写成官方契约。

旧教程样本存在“等级高于上限、觉醒数却为零”的不自洽组合，只能辅助核对字段形状，不能反推出全部公式。对缺来源的数值，明确使用重建默认或保持拒绝；不以默认值冒充原服真值。
