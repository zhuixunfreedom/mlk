# 公会与公会战契约

本章按 CN3.5 客户端页面消费与本项目重建整理。普通公会战、公会任务、协力战是不同链路。文中保留协议结构和机制解释，示例不含真实设备标识与公会／账号数据。

## 页面依赖

| 页面 | 数据键与路径 | 进入条件或消费 |
|---|---|---|
| GuildTop | guild、battle_condition 来自 `/guilds/`，以及 user、编队、单位 | guild 为空可转未入会页 |
| GuildDeck、GuildDefenceDecks | guild_deck→`/guilds/deck`，guild_monsters→`/guilds/monsters` | 对象槽位 0–4 |
| GuildMonsters | guild_monsters | 魔宠选择行 |
| GuildEquipmentScrollable2 | guild、user、guild_equipment_types | 列表数据键须由同源或前置响应提供 |
| GuildMembers | guild 与 guild_members | ListParts 明确 data_key；不能只提供 users_map 却漏列表 |
| GuildSettings | search_index→`/guilds/search_index` | 招募、审批、参战和设置 |
| GuildRecruit | guild_subscriptions→`/guilds/subscriptions` | 申请者与审批 URL |
| GuildWaitingList | `/waiting_users` | 邀请／挂起读面，完整流程范围另行确认 |
| GuildDescription | `/guilds/show?with_search_index=true&id=` | 临时公会与搜索配置缓存 |
| GuildRankingsPage | guild_rankings→`/guild_rankings` | 排名列表与奖励说明 |
| BattleSelect | user_units、user_monsters、user_decks | 按 mode 进入对应战斗链 |

读数据逻辑仍可能发外层加密 POST，需要对应注册方法。requireData 成功只证明拿到数据，不证明每个按钮和设施规则完成。

## guild 与成员

| 字段 | 形态 | 客户端用途 |
|---|---|---|
| id、name、master_name | string | 身份、名称和会长显示；不提供真实值 |
| users_map | object | 成员集合与计数 |
| rating | int | 评分显示 |
| rank_id | string | 枚举短名 |
| guild_ranking_point | int | 公会排名积分 |
| guild_ranking_rank | string | 名次显示 |
| equipments | object | 按设施 type_id 取文档 |

成员角色文档 guild_role.id 中 1/2/3 为成员、副长、会长。客户端按钮可按角色显示，服务端仍须重新鉴权。目标用户 ID 不能只因 UI 隐藏按钮就假定合法。

## 战况、时窗与背景

battle_condition 包含 guilds 列表与 condition；列表项有 id、name、rank_id、ranking、point、color、joined，condition 有 combo、power、seed_powerup_rate。BattleCooperate 分支另带 monster，其普通战规则不能由该结构反推。

fields 每行提供 begin_hm、end_hm、bg_name、actable、ranking_enable、祈祷／应援／攻击成本和计数。已有客户端判开场依赖当前字段 bg_name 非空和 battle_condition 非空，可行动再看 actable。

只在有效可战时段下发战场背景，其余 bg_name 留空。旧回退路径可能使用首行 fields；若所有行都给背景，休战幕布与战场画面可能重叠。背景名应指向实际存在的客户端资源，不能随意新造逻辑名。

pray_bp/pray_gp、help_bp/help_gp 和 attack_bp1–3 决定按钮价目；已见客户端回退数值分别为 15/400、25/500、30/50/70。回退值说明客户端默认，不证明原服完整经济规则，也不固定所有部署当前配置。

## 设施、共享魔宠与辅助键

guild.equipments 按 hp、sp、taghness、at 及 temporary 等类型组织，行含 asset_name、name、description、effect、point，以及 current.level/until/end。玩家资材看 user.guild_asset_count，投资不能信任客户端余额。

辅助数据还包括 guild_equipment_types、fields、battle_weapon_rate、battle_difficulty、my_shared_monsters、my_guild_memo、guild_member_option、search_index，以及创建／搜索的选择选项。文档中的字段名是 schema，不保留真实留言或成员资料。

user 的公会归属与角色、BP 和资材应随同源快照更新。my_shared_monsters 的两格与防卫编队是不同数据关系，不因都显示魔宠就合并状态。

## 写路径

| 路径 | 参数或语义 | 服务端要求 |
|---|---|---|
| `/guilds/create.json` | name、play_type_id、approval_type_id、recruit_text | 建会与归属同事务 |
| `/guilds/search.json` | keyword、类型过滤、可选 recommend | 不公开实际搜索输入 |
| `/guilds/update` | 类型设置、招募文案或 memo | 重新校验角色权限 |
| `/guilds/set_shifts` | 0–6 的参战布尔值 | 持久化星期设置 |
| `/guilds/dropout` | 自退，或 id/target_user_id | 区分自退与管理权限 |
| `/guilds/change_master` | id、target_user_id | 转让角色和归属一致 |
| `/guilds/change_sub_master`、`/guilds/fire_sub_master` | id、target_user_id | 当前权限和目标归属校验 |
| `/guilds/reject_all_subscription` | 拒绝申请 | 副长等角色限制 |
| `/guilds/set_deck` | party_index、uuid | 实例归属与槽位校验 |
| `/guilds/remove_from_deck` | uuid | 与防卫／共享关系一致 |
| `/guilds/invest` | equipment_type_id、value | 条件扣资材与设施写入同事务 |
| `/battles/help`、`/battles/pray` | 动作请求，读 animation_message | BP、GP、效果和台账一起提交 |
| `/battles/guild_quest_execute.json` | mode=battle、目标 guild_id 等、难度和编队 | 独立公会战会话与快照 |
| `/guilds/guild_quest_execute.json` | 公会任务分支 | 不与公会战合并 |

邀请和审批可能通过 user 文档内嵌 URL 触发，路径由服务端提供。字段已证不意味着所有外围招募流程都已实现。临时设施、推送通知和其他不完整路径应保持明确边界。

## 战斗与结算

公会战 execute 文档与剧情具有共同消费结构，但扣点、result、lose 地址在 `/battles/` 域独立提供。防卫快照至少给可用波次和魔物，空 WaveTable 会触发直接索引风险。

多目标攻击需要冻结每个目标的防卫与效果，波次与资产一同齐备。场次关闭时 prepared（尚未确认扣 BP）的攻击作废；bp_paid（已经进入战斗）的攻击保留结算资格，允许关场后上报胜负。实时排名和最近结果不能重新打开休战背景。

当前重建规则中，应援每次增加 400 SP，祈祷每次增加防卫 HP 2%、AT 2%。普通／困难／极难的掠夺比例由 DifficultyPlunderRate 分别提供为 0.75%／1.5%／2%，按每个被击败目标“当场 session GP”截断计算后转移；不对全历史累计分做同样转移。这些是当前服务端复建值，未取得国服原数值全表。

大怪通过 boss_appear_table 下发，小怪通过 appear_table 的毫秒时间轴下发。多目标大怪按目标公会轮转选取，避免总量截断导致已收费目标没有防卫怪出场。大怪全部击杀触发本轮胜利。以上为同步后的服务端实现，不表示本轮已完成客户端实机验收。

0033 迁移移除徽章商店 BP 药水草稿，启动时同步清理旧生效快照；物品目录中的 BP 药水与玩家已有库存保留。已有玩家库应用该迁移前需要一致性备份。

## 幂等与权限

稳定显式键可用摘要核对、结果重放和同键异参拒绝。无键 help/pray 不应承诺所有网络重发都被永久去重；连续合法动作必须可以各自生效。battle_id、guild_id、槽位、资材和角色校验在服务端执行，不能依赖客户端显示状态。

终结后重开新战斗应有新会话；重复 result/lose 不重复入账，跨账号 bid 拒绝。事件台账、余额、效果和结算快照必须在同一事务边界组合。

## 历史验证与未开放范围

2026-10-02/03 曾分批验证过建会、搜索、成员互见、防卫持久化、设施投资、时窗、祈祷应援、单／多目标与关窗、重启和部分结果回放。这些是当时的已测范围，未经客户端重跑。

测试临时时窗和隔离库解锁不属于官方协议事实。显示加载指南可能需要点击才开战，不能一律判为挂死。成员列表修改 data_key 后需要更新配置版本并确保客户端取到新配置。

协力战规则、BP 水库、临时设施完整链、部分招募回执和后期其他版本机制没有足够 CN3.5 证据，不因相近字段名而添加。
